**Being built on branch `wl/wl-mv7hiabx2ozy80`.** Workload `wl-mv7hiabx2ozy80` (normal stakes, plan revision 2 at `~/agent-scratch/agent-system-2.0/wl-mv7hiabx2ozy80/PLAN.md`, approved by Jo in `in-mv8cbrm3igai2o` on `q-mv7ikj5jmpxpfk`). **The rule** (Jo, ledger inputs `in-mv7hm58386f2o0` and `in-mv7hmuk0u600e8`): a permanent default for every lane, not an override for the workloads that prompted it. A hand that is not a review runs on the lab of the lane that spawns it, tier for tier; a review hand stays cross-lab. **The problem it fixes:** every tier row in `profile/config.yml` lists its Anthropic entry first, and a non-review spawn was given the whole row in that order, so a lane running on OpenAI or Kimi dispatched its build hands to Anthropic, with the other labs' entries only as fallbacks behind it.

**What changes** (SPEC-2.0.md § A1.3 *Amended 2026-10-14 — build hands follow the lane's lab* and § B11 *Amended 2026-10-14 — build fallback stays in the lane's lab*; DESIGN-2.0.md dispatch chain and P-11 row 15).
- Kind, tier and stakes cap are chosen as before. At a non-review spawn the classifier (`classifier/extension.ts`, `before_subagent_spawn`) then keeps only the tier row's entries whose lab, by `labOf` in `classifier/src/lab.ts`, is the lab of the spawning session's current model (`provider/id`), in row order with their thinking suffixes. The plan places that selection in a small helper, `classifier/src/build-row.ts`.
- Tier for tier, not model for model: an OpenAI lane's strong build runs the strong row's OpenAI entry, an OpenAI lane's deep build the deep row's OpenAI entry; neither has to be the lane's exact model.
- Fallback stays inside the kept entries: same lab, same tier. With today's profile each tier row holds one entry per lab, so in practice the lab's single entry runs or the dispatch is refused.
- Refused before any hand runs: the lane's current model is missing or its provider has no lab; the tier row has no entry of that lab; every same-lab entry is unusable (absent from the registry, a disabled provider, no credentials, a `provider-refused:`). Nothing falls back to another lab's entry, to OMP's native row, or to the lane's own model.
- The kept entries are the hand's row wherever a row is used: the candidates returned at spawn, the `hand-spawn:` row, and the settle allowlist, so output from a hand that answered on another lab is withheld as out of row. A hand keeps the row pinned at its spawn if the lane later switches models or the result is recovered after a restart; a model switch affects later spawns only.
- A tier spawn with no classification gets the same restriction. This adds no nested dispatch: hands stay leaves.

**What does not change.** Classification, kind → tier, the stakes caps and the profile's tier selectors (`task.agentModelOverrides` is byte-for-byte unchanged; only its comments were rewritten). Reviews (a judge slice, or a low-confidence brief with judge among its two likeliest kinds) still plan on `reviewRow` and § B4's cross-lab rule: builder provenance read from the ledger, effective stakes, production fan-out, `same-lab` / `wait` parks and grants, the review round limit, the reviewer cost rule (`REVIEW_ROW_FROM`), and Jo's Kimi-out standing rule (`migration/items/kimi-out-reviews-run-same-lab.md`). A lane's builder history from before this change, including a workload whose builders span two labs, is kept as recorded.

**The trade.** Build failover to another lab is gone: when the lane's lab cannot serve the tier, the build is refused rather than spent on another lab's subscription. Different providers mapped to the same lab may still supply same-tier fallback entries. Reviews keep their cross-lab candidates.

**Verification, owed by the workload's later slices.** None of these has a result recorded in this item yet. Regression cases written before the change and run on an unpacked baseline (`1703ed1e6545725a2ad85eba01617ccc344f2fca`) to show assertion failures (`FAILS-BEFORE.md` beside the plan); the focused classifier tests named in the plan on the built tree; a live run of a lane whose model is exactly `openai-codex/gpt-6.1-sol`, dispatching a build hand and recording the tier, the candidates, the answering models and the usage, with no Anthropic build-hand turns (`ACCEPTANCE.md` beside the plan); a cross-lab review of the diff; and `lane_full_test` green at the PR head. When they land, the receipts go in the PR body and this item's `pr:` is set.

**Rollout.** The rule is code in the classifier, which each lane process loads once from the main checkout (`{repo}/classifier/extension.ts`, profile `extensions:`). After Jo merges: fast-forward the main checkout, re-run the install so the installed profile carries the rewritten comments, and relaunch every running lane. A lane that is not relaunched keeps routing its builds on the whole row until it is.

**Reversal.** Revert the PR on main, fast-forward the main checkout, re-run the install, and relaunch the running lanes; builds then take the full cross-lab row again. Builder provenance written while the rule was live stays in the ledger and keeps counting for reviews.
