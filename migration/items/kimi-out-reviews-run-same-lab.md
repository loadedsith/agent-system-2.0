**What the classifier does now** (`classifier/extension.ts`, `classifier/src/lab.ts`).
- The rule is decided at one place, the review hand's spawn, where the usable row, the builders and the clock are all known. A spawn whose review plan is a park runs the review same-lab when all hold: the rule is active (`kimiOutRuleActive(now)`, read inside the spawn's write transaction); builder provenance is known and Kimi is not a builder lab; no entry of the review row is on a provider with no lab; there is Kimi-out evidence (below); and a same-lab hand is runnable.
- Kimi-out evidence is one of: every kimi entry of the review row (`moonshot/*` and `kimi-code/*` alike) is skipped as unusable (not in the registry, provider disabled, no credentials, or a `provider-refused:` on its provider); or the row has no kimi entry and `KIMI_OUT_RULE.rowOmission` is set, the rule's dated declaration that the installed rows dropped moonshot for this outage. A `provider-refused:` counts as evidence only when its `token <dt>` has a `hand-spawn:` written before it on the workload, so a refusal citing a token that never ran is ignored for the rule.
- Instead of the question the classifier writes, as the lane id and in the same transaction as the hand's `hand-spawn:` (immediately before it), one entry: `review-same-lab-rule: in-mv5xafhywe3w8w slice <sliceId> token <dt> labs <lab,lab> kimi <why Kimi was skipped>` (`reviewSameLabRuleBody` / `parseReviewSameLabRule` in `lab.ts`). It is both the record and the spend: no question, no `review-park:`, no `review-same-lab:`, and the slice is not paused. `kimi …` records the missing Kimi leg (for example `no kimi entry in the deep review row (KIMI_OUT_RULE.rowOmission)`), and the routing note adds `kimi leg missing: <evidence> (Jo's rule in-mv5xafhywe3w8w)`. The `review-round:` format is unchanged.
- A production review whose planning finds no other lab is not failed at the `task` call when the same checks hold there: it is published as one hand (no fan-out) and the spawn decides. A production fan-out whose members all ended with no accepted review raises no question only when one of the group's own member tokens carries a Kimi `provider-refused:` (401 / 403, or the quota 429 below) after its `hand-spawn:`, with no `provider-ok:` since (a concurrent group's later refusal does not hide it), and every kimi entry of the current review row is skipped by `usableRow` on the live registry, disabled providers and credentials of the latest session context the lane process saw (none seen yet: it asks). It writes nothing, and the re-dispatch reaches the spawn, which runs same-lab or asks. Because that check awaits, a group whose check ends in a park yields instead when a newer review dispatch of the slice has begun meanwhile (`supersededSince`): the newer round decides. If that newer dispatch is then refused before it publishes, the question waits for the lane's next dispatch, which plans again (code review of 6be06f2, finding left as is).
- The round limit is untouched: a failed round at the limit still raises the `review-limit:` question; after Jo's `extend` the next dispatch reaches the spawn, which applies the rule if it is still active.
**Which parks still ask Jo.** Every park the rule does not cover raises the same-lab / wait question as before: Kimi is a builder lab; builder provenance is unknown; the row names a provider with no lab; a kimi entry is still usable (including a second kimi provider when only the first refused); nothing same-lab is runnable; a single review hand that ended with no assistant turn (silence is not Kimi-specific); a fan-out end after an ordinary 500 or a plain 429, a refusal at spawn, a silent member, a withheld review that changed the work, or no settled row; any park once the rule has ended, including a spawn whose clock crossed the end after its `task` call was planned.
**The end.** `KIMI_OUT_RULE.endsAt` in `classifier/src/lab.ts` is `Date.parse("2026-11-01T00:00:00-07:00")`, the end of 2026-10-31 America/Los_Angeles (PDT); `kimiOutRuleActive(now)` is `now < endsAt`, with `now` from `ClassifierDeps.now` (default `Date.now`). After it every Kimi-out park asks again and the quota refusals stop being honoured. Ending it early on Jo's word: set `endsAt` to the moment of Jo's word, merge, fast-forward the main checkout, and relaunch the lanes.
**Quota marking, Kimi only and bound to the window.** While `kimiOutRuleActive(now)`, a failed dispatch whose errors include a 429 from a kimi-lab provider (`moonshot`, `kimi-code`) with a quota or suspension message (`exceeded_current_quota`, `insufficient balance`, `suspended`; case-insensitive) writes `provider-refused: <provider> status 429 token <dt>`, so later spawns on the workload skip that provider until the surface writes `provider-ok:`. Without it a Kimi-only review whose Kimi answers 429 loops through failed dispatches and never reaches a park. Every other 429 writes nothing, as before: a non-kimi provider, a plain rate-limit 429, or any 429 after the end. A `status 429` refusal is honoured only while the rule is active, so after the end Kimi is usable again without a `provider-ok:`; 401 / 403 refusals behave as before.
**Lane tools.** `lane_record_entry` now refuses bodies opening with `review-same-lab:`, `review-same-lab-rule:` and `provider-refused:` (beside `hand-spawn:` / `hand-settled:`), so a lane cannot grant itself same-lab, forge a spend, or manufacture the Kimi-out evidence through its own tool; `provider-ok:` stays the surface's. `planReviewed` (`surface/extensions/lane-tools.ts`) counts a same-lab plan review only when the entry that let it run is immediately followed, by the same writer, by that token's `hand-spawn:` on the plan slice, and that entry is Jo's spent same-lab answer to a park question of the slice or a `review-same-lab-rule:` entry for the slice. `CLASSIFIER_MACHINERY_PREFIXES` (`surface/src/launch.ts`) gains `review-same-lab-rule`.
**Least-involved builder lab first.** A same-lab plan orders the builder labs' entries by how much the lab built, least first, then row order: a lab with no recorded role, then a lab that is a builder only through review hands (withheld or unsettled), then one through non-review hands, then a lane's lab (`builderRoles` in `lab.ts`, sharing `builderLabs`' walk). The rule's `labs` field lists that order, and Jo's own `same-lab` grants now use it too. With one builder lab nothing changes.
**Running lanes.** The classifier loads once per lane process from `/Users/jowolff/code/agent-system-2.0/classifier/extension.ts`, and hands run in the lane's process. After Jo merges, the main checkout is fast-forwarded (item 91) and each running lane relaunched; until then a running lane still asks and Ilex relays same-lab under the rule.
