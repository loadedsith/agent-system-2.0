# Lane launcher — design

Status: ruled 2026-09-30 (Jo: Q1/Q2 per Plumb's recommendation); build not started.

Scope: how an open workload gets a live lane session, how that session is configured, how it lives and dies, and how the orchestrator (Ilex) and Jo see it. Written from the three-lab quorum synthesis (`~/agent-scratch/agent-system-2.0/migration/M7/lane-launcher/SYNTHESIS.md`) under Jo's two rulings. Nothing here is built; pseudocode is illustrative. Every code fact carries a repo-relative `file:line` and a quoted anchor so the reference survives edits; OMP facts cite the installed 18.4.4 source under `@oh-my-pi/pi-coding-agent/src/`.

**QUESTION — ledger schema v6 or not.** The holder-checked release (decision 5) can be enforced at two levels. *File level* (a trigger beside `workloads_holder_no_steal`, `ledger/schema.sql:416`, plus typed launch rows) is schema version 6 — and the module has no upgrade path: a file at an older version "is refused unchanged: move it aside and install a new ledger" (`ledger/src/index.ts:31-33`, `LedgerSchemaVersionError`). Jo's live ledger holds the standing workload and the two real M7 workloads, so v6 costs a reinstall plus a by-hand copy of those rows. *Module level* (`releaseWorkload` gains a required `holder` and a `WHERE holder = ?`; launch facts stay prefixed `assumption` entries like `repo:` and `artifact-command:` today) is schema-neutral and covers the threat model — accidental misuse by the system's own lanes (SPEC § A4), whose raw writes P-11 row 10 and the OS fence already refuse. Recommendation: **module level now, no v6**; the trigger text is written below and waits for the next natural schema bump. The page proceeds on that recommendation; every line that changes under v6 says so.

## 2. Decisions

Each decision names the fork it closes (A–L in SYNTHESIS.md § 2) and the lab whose shape it takes. Rulings first, then the transfer list.

1. **Who starts a lane — fork A, Claude's shape plus Kimi's predicate (Jo's ruling Q1).** At `orchestrator_open_workload`, after the row and the `repo:` entry are written (`surface/extensions/workload.ts:70-71`, `ledger.openWorkload(…)` then `recordRepo(ledger, id, repo)`), the surface extension evaluates one pure launch predicate and, when it says launch, execs the lane starter (`surface/scripts/lane.ts launch`) through the extension API (`pi.exec`, `extensibility/extensions/types.ts:1578`, "Execute a shell command") — not through the bash tool, so P-11 row 15 never sees it. The same predicate runs again on the existing 60-second poll (`surface/extensions/wake.ts:124`, `timer(() => poll(s), s.pollMs)`; `POLL_MS = 60_000`, `surface/src/types.ts:74`) as catch-up: a crash between open and spawn, or an orchestrator that was not running at open, is repaired within a minute by the same function. There is no separate supervisor process (Codex's shape is not taken: a second long-lived process whose own liveness must be recorded and watched). The predicate excludes the standing workload, `due:` rows (`DUE_PREFIX` briefs written by `orchestrator_schedule`, `surface/extensions/workload.ts:137`), and user-driven workloads (§ B13.1 "mode = who is steering"): those two never auto-launch, and the open tool's result carries the by-hand command instead (decision 14).

2. **What an autonomous lane process is — fork B and fork C, Claude's shape (Jo's ruling Q2).** One `omp --mode rpc --no-ui …` process per lane, started in the worktree, given exactly one `prompt` frame (`modes/rpc/rpc-types.ts:29`, `type: "prompt"`), and waited on for its one `prompt_result` (`modes/rpc/rpc-prompt-results.ts:145-148`, `type: "prompt_result"`, `status: outcome.status`; statuses `"completed" | "aborted" | "error"`, `rpc-types.ts:149`). A small **detached per-lane runner** (Bun script, its own session, not a child of the orchestrator's process tree) holds stdin/stdout, writes the log, and on any exit of `omp` — clean, error, deadline, or SIGKILL — releases the workload if the holder is still this lane, within seconds. Exit is typed: the runner closes stdin after `prompt_result`, and stdin EOF makes OMP drain, dispose the session (which "also emits `session_shutdown`", `modes/rpc/rpc-mode.ts:1725`) and exit 0 (`rpc-mode.ts:1760-1774`, "stdin closed — RPC client is gone … return disposeAndExit()"), so the existing lane row's shutdown handler (`surface/extensions/lane.ts:127-144`, `pi.on("session_shutdown", …)` … `ledger.releaseWorkload(w.id, …)`) runs on the clean path and the runner is the belt-and-braces for the unclean one. The same path covers the runner's own death: the runner holds the only write end of `omp`'s stdin, so when it dies the pipe closes and `omp` releases at the end of its in-flight prompt (§ 6). Not adopted: persistent turn-by-turn rpc driven from ledger state (Codex), and print mode `-p` (Kimi: no typed exit, nothing can abort it). `--no-ui` is legal only with `--mode rpc` (`main.ts:250-254`, "`--no-ui` requires `--mode rpc`").

3. **Where a lane works — synthesis "Needs you" item 1 and fork K, Claude's alternate.** The OS fence's first deny target is the ledger *directory*: `fenceTargets` opens with `{ kind: "subpath", path: canonical(dirname(ledgerPath), "the ledger directory") }` (`gates/src/fence.ts:201`) and the default ledger path is `$HOME/.agent-system-2/ledger.db` (`ledger/src/locality.ts:14-18`, `defaultLedgerPath`). Every bash call a lane makes runs under that Seatbelt profile (`fence.ts:229-231`, `(deny file-write* (subpath …))`), so a worktree anywhere under `~/.agent-system-2/` cannot be committed to, built in, or tested in. Worktrees therefore live **beside the checkout**: `<parent>/<repo-basename>-lanes/<workload-id>/` (for this repo, `/Users/jowolff/code/agent-system-2.0-lanes/wl-…/`), on branch `wl/<workload-id>` cut from the remote's default branch when an `origin` exists, else from the local default. Inside the repo (`<repo>/.worktrees/`) was checked and rejected: the fence would allow it — for a directory inside a repository the fence denies only the `.git` entry itself (`fence.ts:175`, `out.push({ kind: "literal", path: dotGit })`) and the common `hooks` directory (`fence.ts:185`) — but the brief's install rule says state "never enters the repo", and an untracked directory inside the checkout is state in the repo. Cleanup is an explicit `as2 lane cleanup <workload>` (Claude and Codex), refused while the worktree is dirty or its branch has commits not on the remote; the branch is never deleted (reserved, § A4). The close tool does not touch worktrees (Plumb's draft had it remove them at close; no lab put cleanup there). Relaunch reuses an existing branch and worktree: `git worktree add <path> wl/<wl>` without `-b` when the branch exists, and nothing when the worktree is already registered (Codex's attack on Kimi's unconditional `-b`).

4. **How a lane writes the ledger — fork E, Codex's shape.** No registered tool today adds or completes a slice, raises a question, enqueues a message, or releases: the by-hand script did all of it through the module from outside OMP (`~/agent-scratch/agent-system-2.0/migration/M7/lane-by-hand/wl-munn32rmt6ajnk.ts`, `ledger.addSlice`, `completeSlice`, `enqueue`, `releaseWorkload`). A bash CLI cannot do it from inside a lane: the fence denies the SQLite write at the OS level and has no script exemption (Claude's attack on Kimi). The lane gets **extension tools**, registered in the surface's own extension the way `slice_artifact` is (`surface/extensions/lane.ts:81-107`, `pi.registerTool({ name: ARTIFACT_TOOL, loadMode: "essential", …`), `loadMode: "essential"` so they are top-level and not `xd://` devices (M7 finding 1). Exact list and inputs in § 4. Every one validates ownership before writing: the session is a bound lane, the workload is this lane's, the holder is this lane with a live lease, and a named slice belongs to the workload.

5. **Holder-checked release — fork D, Codex's shape at module level (see the QUESTION above).** `releaseWorkload` today updates `WHERE id = ?` with no holder condition (`ledger/src/index.ts:471-476`, `UPDATE workloads SET holder = NULL, holder_lease_until = NULL … WHERE id = ? RETURNING id`), so a stale lane can release a live one. It becomes `releaseWorkload(id, { by, holder })` with `AND holder = ?` in the predicate; zero rows is a typed refusal (`not the holder`), not `expectOne`'s generic error. Identity has three parts, Codex's shape: the **lane id** `lane-<workload-suffix>-<n>`, where `n` is minted inside the same `BEGIN IMMEDIATE` transaction as the cap check and the pre-claim (`ledger/src/index.ts:428-431`, `write<T>(fn)` "Run `fn` in BEGIN IMMEDIATE") so two concurrent starts cannot mint the same ordinal (Codex's attack on Claude); the **PID** and the **process start time** of `omp`, recorded by the runner in a `lane-started:` entry. The lane id is what the ledger checks. The runner signals `omp` only through its own child handle (`child.kill()`), before the child's exit event, so it never needs the PID; PID and start time are what `as2 lane stop` re-reads before signalling an `omp` whose runner is gone, so a reused PID is never killed.

6. **Mode flip on a running lane — fork J, Codex's shape.** Jo's one-word flip lands as today (`flipMode`, `ledger/src/index.ts:485-497`, "the mode-flip instruction and the flip land in one transaction"). For a running autonomous lane the surface then writes a `lane-stop:` entry naming the reason `mode-flip`; the runner sees it on its ledger poll, sends `abort` (`rpc-types.ts:33`, `type: "abort"`), closes stdin, and records `lane-exit: … reason mode-flip` — no `lane-died:`, since the exit was requested. The open tool's result and the wake render then carry the by-hand command `as2 lane <workload>`, which relaunches **interactively** with `--resume <session path>` on the same worktree and binding. The reverse flip (user-driven → autonomous) is Jo leaving the interactive session and saying the word; the surface writes `launch-requested: by jo (mode-flip)` in the same transaction as the flip, so the predicate (decision 7: a request newer than the newest attempt) launches an autonomous lane with `--resume <recorded session>` — no separate `orchestrator_launch_lane` call. **Plumb's draft's `steer` over the held pipe is not adopted**: a one-prompt rpc lane has no second prompt to steer into, and the labs' shape (stop at a boundary, relaunch in the other mode) needs no pipe kept open across the flip.

7. **Never auto-restart — fork F, Claude and Codex.** A lane that dies writes (or has written for it) a `lane-died:` message; the surface pushes it to Jo (decision 9); Jo, or Ilex on Jo's word, relaunches with `orchestrator_launch_lane`. Kimi's one automatic retry is not taken: it relaunched a finished-but-unclosed workload (Claude's attack) and could not recreate a worktree it had already made (Codex's attack). The launch predicate encodes this: a workload with any prior launch attempt is launchable again only when a `launch-requested:` entry is newer than the newest attempt (or, for a parked lane, an answer is newer than its `lane-parked:`, decision 14). A launch attempt is a `launch:` entry, and only `reserveLane` writes one, in the transaction that mints the lane id (decision 8); a refusal at the cap, on a held workload or on a closed one writes nothing.

8. **Global cap 3, atomic — fork G, Claude's number with Codex's atomicity.** At most three autonomous lanes hold workloads at once (`AGENT_SYSTEM_MAX_LANES`, default 3). Count-then-claim is one ledger transaction: a new module method `reserveLane(workloadId, { by, cap, leaseMs })` runs, inside one `write()` (BEGIN IMMEDIATE, `ledger/src/index.ts:429-431`), the live-lane count (open autonomous workloads whose holder matches `lane-*` and whose lease is null or not yet expired), the ordinal mint, the pre-claim (the `claimWorkload` update with `by: "lane-starter"`, `holder: laneId`, a 3-minute lease), and the attempt entry `launch: <laneId> requested-by <who>` (an `assumption` entry, `by: "lane-starter"`); it returns `{ ok: true, laneId }` or `{ ok: false, reason: "cap" | "held" | "closed" }`. A refusal returns before any write: no `launch:`, no `launch-failed:`, no message, so a refused workload's predicate inputs are unchanged and the tick launches it once the reason clears. `launch-failed:` is written only for a failure after a reservation (decision 9). The stamp is `"lane-starter"`, never the lane id, because `claimWorkload` sets `changed_by` from `by` on every winning update (`ledger/src/index.ts:458`, `UPDATE workloads SET holder = ?, holder_lease_until = ?, changed_by = ? …`) and the lane row's own claim stamps the lane id (`surface/extensions/lane.ts:74`, `ledger.claimWorkload(w.id, { by: s.laneId, holder: s.laneId, …`): the workload's `changed_by` becomes the lane id only when the lane's extension has loaded and bound, which is what readiness (decision 14) observes. SQLite's write lock serializes writers across processes, so a fourth concurrent start sees three and refuses (the sequential "refuses the fourth" test that Codex called insufficient is replaced by a concurrent one, § 8). The pre-claim's three-minute lease is the launch readiness window (decision 14).

9. **Launch failure rides `lane-died:` — fork I, Claude's shape.** Between wakes, the poll delivers only § B3 error lines (`surface/extensions/wake.ts:26-31`, `readLines` → `errorLines`), and among lane-to-orchestrator messages only three body prefixes ever become lines: `lane-died:` (source 4, `surface/src/errors.ts:19-20`), `prompt-wait:` (source 5, `errors.ts:21-22`) and `artifact-failed:` (source 3). Any other message to the orchestrator is consumed at the next read, never pushed (`surface/src/delivery.ts:64-66`, `advanceMessage(id, "delivered", …)`). So a launch failure after a reservation writes a `launch-failed:` entry **and** a message `lane-died: <laneId>: launch failed at <stage>: <reason>` — the body shape `laneDeaths` parses (`surface/src/signals.ts:48`, `/^lane-died:\s*(\S+?):\s/`) — and Jo sees it within one poll. When the launch is synchronous with a tool call (open, or `orchestrator_launch_lane`) the tool result carries the same line too. Codex's workload-level `question` rows would need `raiseQuestion` to accept a null `sliceId` (`ledger/src/index.ts:596`, `sliceId: string`) and a schema change; not taken.

10. **Lanes survive `as2` exiting — fork C, all three labs against Plumb's draft.** The runner is detached from the orchestrator's process (its own session; stdio to its log, never to the orchestrator's pipes), so closing the orchestrator terminal, `/exit`, or a crash of `as2` leaves every lane running. The orchestrator on relaunch reads the ledger (wake, § B7) and finds the live holders; nothing is resumed or aborted on its behalf. Plumb's draft had lanes as children that get `abort` on exit and resume on the next open; unanimous against.

11. **Converged bundle — no fork, and fork L (Claude and Kimi: no gates edits).** Worktree-per-workload on its own branch, never in the checkout (decision 3). Per-lane `--session-dir` — `~/.agent-system-2/lanes/<workload-id>/sessions` — never `--no-session`: with `--session-dir` and no `--resume`, OMP creates the new session there (`main.ts:1232-1235`, "If --session-dir provided without --continue/--resume, create new session there"); `--resume <path>` with a `/` or `.jsonl` in it opens exactly that file (`main.ts:1186-1187`). Binding by the three env vars (`gates/src/types.ts:25-27`, `ROLE_ENV = "AGENT_SYSTEM_ROLE"`, `WORKLOAD_ENV`, `LANE_ENV`) with the inherited `AGENT_SYSTEM_ROLE=orchestrator` — which `as2` sets (`bin/as2:85`, `exec env OMP_PROFILE="$PROFILE_NAME" AGENT_SYSTEM_ROLE=orchestrator omp --cwd "$REPO"`) and the starter would inherit — **overwritten to `lane`**, since the gates read role as orchestrator whenever that variable says so (`gates/src/session.ts:83-85`, `roleOf`). This repo lands by Jo integrating: the lane commits on `wl/<wl>`, rebases onto the remote default (row 8's upstream when the branch tracks nothing, `gates/src/rows/r08-push-rebase.ts:21-23`), pushes with `-u`, opens the PR, and never merges; product repos the same. The decision-log context the open tool already renders (`surface/extensions/workload.ts:73`, `decisionLogContext(logDir(repo), { since })`) reaches the lane inside the launch prompt, a real pipe, not a file the lane is hoped to read. A fake `omp` shim on PATH for unit tests and a chaos smoke are in the build (§ 8). The gates are not edited: Codex's rewrite of row 7 into a pre-execution readiness gate is out of scope per the quorum brief; readiness is the runner's concern (decision 14).

12. **`--max-time` and the ceiling — fork H, Kimi's env with Codex's ceiling tie.** `--max-time` is OMP's only hard cap: it sets one deadline from process start (`main.ts:1299-1300`, `options.deadline = Date.now() + parsed.maxTime * 1000`) and the agent loop ends its stream once passed (`@oh-my-pi/pi-agent-core/src/agent-loop.ts:1095-1096`, `isDeadlineExceeded`; the deadline timer aborts the loop, `:1179-1191`). No token cap exists and none is claimed. Default **2 h**, env `AGENT_SYSTEM_LANE_MAX_TIME` (a duration OMP parses: "5s", "10m", "1h", `cli/flag-tables.ts:88-104`). Claude's attack on Codex — the deadline ends the loop, not the process, so a persistent lane keeps renewing its lease — does not apply here: the loop ending produces the `prompt_result`, the runner closes stdin, the process exits. Once the workload ceiling exists (not built: MIGRATION.md M7 row, "**the workload ceiling is not built**"), a lane's cap and each hand's ceiling-share derive from the workload's *remaining* ceiling with the lane's own tokens counted (Codex); until then the fixed default stands and row 5's numeric check is not budget enforcement. This page states the dependency and designs nothing of the ceiling.

13. **The close tool commits its own decision-log entry — Jo's ruling 2026-09-30 (M7 finding D).** Today `orchestrator_close_workload` renders the entry (`surface/extensions/workload.ts:114`, `renderClose(ledger, id, logDir(repo), identityOf(ledger))`) and closes the row (`:115`), leaving the file untracked. It gains one step between render and close: `git -C <repo> add <path>` and `git commit -m "docs: decision-log entry <slug> (workload <wl>)" -- <path>` through `pi.exec` (machinery, not the bash tool), committing only that path on the checkout's current branch. A commit that fails (no identity, a merge in progress) does not block the close; the tool result names the untracked path and the reason. Part of this build round.

14. **Unique ideas adopted.** *Parked on a question is not dead* (Claude): a lane whose prompt ends with an open `question` row on its workload is **parked**. The runner writes `lane-parked: <laneId> question <qid> session <path>`, then closes stdin, and `omp` takes the same EOF path as a clean finish (decision 2): `session_shutdown`, release. No `lane-died:` fires. The lane row's shutdown handler counts paused slices as in flight today (`surface/extensions/lane.ts:140`, `const inFlight = w.open_slices + w.paused_slices`); it gains one check, skipping the death line when the newest `lane-parked:` entry names its own lane id, which the runner wrote before closing stdin. The question is already a § B3 item 5 line (`surface/src/errors.ts:21-22`, source 5, "every open `question`"), and a slice pauses only on an open question (`ledger/schema.sql:441`, `slices_pause_needs_question`). A parked lane holds no process and no cap slot. Jo's answer lands as the `answer` instruction the surface already writes (`surface/src/input.ts:77-78`, `ledger.answerQuestion(cmd.questionId, …)`), and the predicate's parked-then-answered rule relaunches the lane with `--resume <session path>` from its `lane-parked:` entry; the surface's answer path runs the same trigger synchronously, so the relaunch does not wait for the next poll. The relaunched lane's first prompt carries the answer text and instruction id, so the round trip of § B3 item 5 completes inside the lane's own conversation. One premise is read, not run, and three paths ride on it — the answer relaunch, the mode-flip relaunch (decision 6), and a relaunch after a death: that `omp --mode rpc --resume <path>` continues the recorded conversation for a new `prompt` frame. What is read is only that `--resume <path>` opens exactly that file (`main.ts:1186-1187`). It is the first real-OMP test (§ 8). *Readiness = the lane's first ledger write* (Codex): not process creation, not the rpc banner — the lane row's claim at `session_start` (`surface/extensions/lane.ts:109-112`, `claim(ctx, "lane start")`), observed by the runner as the workload's `changed_by` becoming the lane id within the three-minute pre-claim window — a real signal because the pre-claim is stamped `"lane-starter"` (decision 8); the runner then writes `lane-ready:`. A launch that never becomes ready is a launch failure (decision 9). *A pure launch predicate* (Kimi): one exported function of plain values, tested as a matrix without OMP (§ 4, § 8). User-driven workloads get the exact by-hand command printed in the open tool's result (Claude and Kimi).

## 3. Process shape

The launch path from open to release, then the catch-up path. `Ilex` is the orchestrator session; `surface` is its extension process; `starter` is `surface/scripts/lane.ts launch`, the short-lived process the extension execs; `runner` is `lane.ts run`, the detached per-lane process the starter spawns (one script, two processes); `omp` is the lane session; `ledger` is the SQLite file.

```mermaid
sequenceDiagram
    participant Jo
    participant Ilex as Ilex (orchestrator)
    participant Surface as surface extension
    participant Ledger as ledger
    participant Starter as lane.ts launch (pi.exec)
    participant Runner as lane.ts run (detached)
    participant Omp as omp --mode rpc --no-ui (lane)

    Jo->>Ilex: "do X"
    Ilex->>Surface: orchestrator_open_workload
    Surface->>Ledger: openWorkload + repo: entry
    Surface->>Surface: launchable(workload, entries, now, cap)?
    Surface->>Starter: pi.exec(bun surface/scripts/lane.ts launch <wl>)
    Starter->>Ledger: reserveLane: count live lanes < 3, mint lane id, pre-claim 3 min by lane-starter, launch: entry (one BEGIN IMMEDIATE; a refusal writes nothing)
    Starter->>Starter: preflight: omp on PATH, profile, repo, fence (a failure: launch-failed: + lane-died:, release)
    Starter->>Starter: git worktree add <repo>-lanes/<wl> -b wl/<wl>
    Starter->>Ledger: worktree:, branch: entries
    Starter->>Runner: spawn lane.ts run detached (own session, stdio → log), exit 0 with lane id
    Surface-->>Ilex: tool result: opened, lane <id> launching
    Runner->>Omp: spawn in worktree: --cwd, --session-dir, --append-system-prompt <tier body>, --max-time, env role=lane
    Runner->>Ledger: lane-started: <laneId> pid <p> start <t> runner <rp> session <path> …
    Omp->>Ledger: session_start: claimWorkload(holder = laneId, 15 min)  ← readiness
    Runner->>Ledger: lane-ready: (observed changed_by = laneId within 3 min)
    Runner->>Omp: {type: "prompt", message: <rendered brief + decision-log context + wake-read instruction>}
    Omp->>Ledger: wake-read entry, slices, hands, artifacts, messages (lane tools)
    Omp-->>Runner: {type: "prompt_result", status: completed | aborted | error}
    alt open question on the workload
        Runner->>Ledger: lane-parked: <laneId> question <qid> session <path>
        Runner->>Omp: close stdin
        Omp->>Ledger: session_shutdown: release (no lane-died:, the lane is parked)
        Omp-->>Runner: exit 0
    else done
        Runner->>Omp: close stdin
        Omp->>Ledger: session_shutdown: lane-died: if work in flight, then release
        Omp-->>Runner: exit 0
    end
    Runner->>Ledger: lane-exit: …; release if holder still laneId; lane-died: unless a clean completion or a park
    opt parked, then answered
        Jo->>Ilex: one-word answer
        Ilex->>Ledger: answer instruction (surface answer path)
        Surface->>Starter: launchable → LAUNCH with --resume: pi.exec(lane.ts launch <wl>)
        Note over Starter,Omp: new lane id; omp --resume <session path>; first prompt carries the answer
    end
    Note over Surface,Ledger: next 60 s poll: recordLapsedLeases, errorLines → lane-died: line pushed to Ilex → Jo
```

Catch-up path (the same predicate on the 60-second tick, `surface/extensions/wake.ts:103-124`, `const poll = …` / `timer(() => poll(s), s.pollMs)`): each poll, after `readLines`, the surface evaluates `launchable` for every open workload and execs the starter for each that qualifies, at most one per poll per workload. What it repairs: a crash between `openWorkload` and `pi.exec`; an orchestrator that was down when Jo relaunched with `orchestrator_launch_lane` from another session; a workload refused at the cap (the refusal wrote nothing, so the predicate still says launch once a slot frees); a parked lane answered before its `omp` had finished releasing (the synchronous trigger on the answer path saw `held`). What it leaves alone: a starter that reserved and then died before spawning the runner — its `launch:` was written in the reservation transaction, so the predicate sees an attempt and returns `died-not-relaunched`; the pre-claim lapses after three minutes, the lapse is recorded as `lane-died:` by `recordLapsedLeases` (`wake.ts:29`), and the workload is *not* relaunched (decision 7) until Jo says so. What it never does: relaunch after a death, launch a `due:` or user-driven workload, or exceed the cap.

Stop path (`as2 lane stop <wl>`, a mode flip, or Jo's "stop"): the surface (or the by-hand command through the module) writes `lane-stop: <laneId> requested by <who> reason <r>`; the runner polls the ledger every 5 s, sees it, sends `abort` (`modes/rpc/rpc-types.ts:33`), closes stdin, waits up to 30 s for exit, then SIGKILLs `omp` through its own child handle (`child.kill()`; no PID re-check, the child has not exited), and finishes as above with reason `stop` — no `lane-died:`.

## 4. Components

| Component | File (new / existing) | Owner | What it does | What it refuses |
|---|---|---|---|---|
| Launch predicate `launchable(w, entries, now, liveLanes, cap)` | new `surface/src/launch.ts` | surface | Pure function of plain values: true when the workload is open, not the standing one, brief not `due:`, mode `autonomous`, holder null or lease lapsed, live lane count below the cap, and either no launch attempt exists or a `launch-requested:` entry (or an `answer` instruction newer than a `lane-parked:`) is newer than the newest `launch:` entry, the attempt `reserveLane` writes. Also renders the argv, env, system-prompt file and first prompt (`renderLaunch`), and the entry bodies | Anything else: it returns a reason string (`due`, `user-driven`, `held`, `cap`, `died-not-relaunched`, `closed`, `standing`) that the tool result and the log carry |
| Open-time trigger and tick catch-up | existing `surface/extensions/workload.ts` (open tool, after `recordRepo`) and `surface/extensions/wake.ts` (inside `poll`) | surface | Calls the predicate; execs the starter with `pi.exec("bun", [laneScript, "launch", wl], { timeout: 30_000 })`; puts the starter's one-line result (lane id, refusal, or typed failure) in the tool result; writes nothing itself (the starter wrote `launch-failed:` and the `lane-died:` message for a failure after its reservation; a refusal wrote nothing). ## 7. Open build questions

Decided when the artifact is written, not here (D6 style). None of these needs Jo.

1. **Detachment mechanics.** Whether `node:child_process.spawn(…, { detached: true })` under Bun plus `unref()` is enough to put `lane.ts run` outside the process tree that OMP's `ptree.exec` manages (`exec/exec.ts:38-45`, `ptree.exec([command, ...args], { … allowAbort: true })`), or whether `lane.ts launch` must re-exec it through `setsid`. One script, so one place for the answer. The chaos test "kill `as2` mid-lane, lane completes" is the arbiter.
2. **Process start time source.** `ps -p <pid> -o lstart=` on macOS versus `proc_pidinfo`, behind one `startTime(pid)` helper in `lane.ts`: the runner calls it once to record `lane-started:`, and `lane.ts stop` is the only caller that compares it before a signal.
3. **First-prompt template.** The rendered brief (workload row, stakes, mode, `repo:`, decision-log context, "call `ledger_wake_read` first", the ledger tools by name) is a `surface/src/launch.ts` template; its exact wording is decided with the tier text. The resume variant (after a park) leads with the answer text and instruction id.
4. **Whether a SIGTERM to `omp --mode rpc` reaches `session_shutdown`.** The interactive path routes kernel signals through `createSessionTeardown` (`modes/session-teardown.ts:2-7`); the rpc path's registration was not traced this session. The design does not depend on it — stop is `abort` + stdin EOF, and SIGKILL is covered by the runner's release — but the fake-omp tests should not assume it either.
5. **`as2 lane` on Linux.** `lane.ts` is Bun, so portable; `ps` flags and `setsid` availability differ. macOS first (the ledger-backup agent has the same note, `install/manifest.tsv:118-120`).
